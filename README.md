# Ghidra processor module for the NXP e200z4 (MPC5746R)

A Ghidra language for the e200z4 PowerPC core of NXP MPC57xx microcontrollers such as
the MPC5746R: VLE-only code, 32-bit GPRs, EFPU2 single-precision floating point, the
Lightweight Signal Processing APU (LSP) and the core MPU.

| Language ID              | Description                                                       |
|--------------------------|-------------------------------------------------------------------|
| `PowerPC:BE:32:VLE-e200` | NXP e200z4 (MPC57xx, e.g. MPC5746R) 32-bit big endian, VLE only, EFPU2, LSP |

The language ID is unchanged from earlier releases, so existing projects keep opening.

## Contents

The language includes Ghidra's own PowerPC SLEIGH sources unmodified (see
`data/languages/UPSTREAM` for the revision) and adds everything e200z4-specific in
separate files:

- `e200_efpu2.sinc`: EFPU2 scalar single precision (`efs*`) for 32-bit GPRs, including
  the fused multiply-adds, `efssqrt`, `efsmax`/`efsmin` and the half-precision conversions.
  Ghidra's SPE versions assume 64-bit GPRs.
- `e200_lsp.sinc`: all 678 LSP instructions with their full semantics: saturation,
  rounding, SPEFSCR overflow bits, register pairs, and circular and bit-reversed
  addressing. Generated by `tools/gen_lsp.py`.
- `e200_isa.sinc`:
  - MPU: `mpure`, `mpuwe`, `mpusync`
  - decorated storage, including the cache bypass forms (`lbdx`, `lbdcbx`, ...)
  - `wait`, `e_ldmvmcsrrw`/`e_stmvmcsrrw`, `nego`, `lwarx` with EH=1, `dcbt`/`dcbtst`
    with a cache target
  - the unsigned saturated math of the e200z425 (`e_addwus`, `e_addhus`, ...)
  - corrections: `e_ori.` no longer decodes as `e_nop`; `e_cmp16i` and related
    instructions are no longer shown as record forms
- `ppc_32_e200.pspec`: e200z4 SPR names (`MCSRR0`, `DSRR0`, `MAS0`-`MAS3`, `MPU0CSR0`,
  `L1CSR0`, `HID0`, ...) and VLE decoding everywhere. It also sets which analyzers run by
  default (see below). Generated by `tools/gen_pspec.py`.
- `ppc_32_e200.cspec`: the PowerPC EABI used by e200 compilers:
  - arguments in r3-r10, floats included; results in r3 (r3:r4 for 8 bytes)
  - structures of up to 8 bytes returned in r3:r4
  - unsigned `char`
  - r2 and r13 (small data area bases) preserved
  - LR as the return address
  - no call fixup. Ghidra's PowerPC specs replace calls to `__get_pc_thunk_lr` with
    `LR = target + 4`. That models the 32-bit `blrl` word that classic PIC code calls to
    read its own address, which VLE code cannot execute.

### PowerPC e200 Constant Reference Analyzer

`src/main/java/.../E200AddressAnalyzer.java` replaces Ghidra's PowerPC Constant Reference
Analyzer (`PowerPCAddressAnalyzer`) for this language; the processor spec disables Ghidra's
analyzer by default. It differs in these ways:

- **Small data area bases.** It assumes the EABI bases r13 (`_SDA_BASE_`) and r2
  (`_SDA2_BASE_`) in all executable memory, so accesses such as `e_lwz r3,-0x7ff0(r13)`
  resolve to global variables instead of `unaff_r13 + -0x7ff0`. The values come from:
  1. register values already set by the loader or with **Set Register Values** (these are
     never changed)
  2. the `_SDA_BASE_` and `_SDA2_BASE_` symbols
  3. the startup code that loads the registers (`e_lis` with `e_add16i`, `e_addi`,
     `e_or2i` or `e_add2i.`), found even when analysis does not reach it

  If the startup code loads different values, for example in an image with a bootloader
  and an application, nothing is assumed and the application log lists the values.
- **VLE instructions.** No references are created from `e_lis`, which holds only the
  upper half of an address, or from constants loaded with `e_li`, `se_li`, `se_bgeni`
  and `se_bmaski`. Ghidra's analyzer checks only the classic `lis` and `li`.
- **Switch tables.** Tables behind `se_bctr` are recovered, with VLE compares as the
  bound on the index, also from flash images loaded into a writable block.
- **Removed:** the PEF and ELF function descriptor handling (r2 as TOC, r30 as GOT), which
  does not apply to the e200 EABI.

On the test firmware, r13 and r2 come from startup code that analysis never reaches. The
results:
- 195 bogus references from `e_lis` disappear
- about 4,400 small data accesses become references
- analysis finds 1,036 more instructions and 22 more functions

### PowerPC e200 Global Data Types

`src/main/java/.../E200DataTypeAnalyzer.java` gives global data of undefined type
(`undefined1`, `undefined2`, `undefined4`, ...) the type the decompiler infers from the
functions that use it. The reference analysis creates such data wherever code loads or
stores a global, knowing only the access size.
- A value used by `efs*` instructions becomes `float`, one that is sign extended becomes
  signed, one that is dereferenced becomes a pointer.
- A type is applied only when the uses agree. A `float` use wins over integer uses of the
  same size, since a value that is only copied looks like an integer. Integer uses that
  differ only in signedness go to a clear majority.
- Single bytes become `byte` or `sbyte` rather than `char`.

It runs after Ghidra's Decompiler Parameter ID analyzer, which commits the decompiler's
function prototypes. Ghidra enables that analyzer by default only for Windows programs;
the processor spec enables it for this language.

A flash image has no RAM, so RAM variables have no data. The decompiler then shows them as
`_DAT_40001234` and warns "Globals starting with '_' overlap smaller symbols at the same
address". The analyzer therefore first adds uninitialized blocks for the MPC5746R RAM,
where nothing is mapped yet, and creates data of the accessed size where code references
it:

| Block | Addresses | |
|---|---|---|
| `SRAM` | 0x40000000-0x4003FFFF | system RAM |
| `IMEM_0`, `IMEM_1` | 0x50000000-0x50003FFF, 0x51000000-0x51003FFF | local instruction memory (rwx) |
| `DMEM_0`, `DMEM_1` | 0x50800000-0x50807FFF, 0x51800000-0x51807FFF | local data memory |

It adds them at the end of analysis. With RAM mapped from the start, Ghidra's Create
Address Tables analyzer takes flash values for pointers into RAM, such as the float 2.0
(0x40000000) or pairs of VLE instructions; on the test firmware that cost 11 functions. The
option **Add MPC5746R RAM blocks** turns this off.

On the test firmware the two analyzers add 13 seconds to the analysis (34 s before, 47 s
after), and:
- undefined data in flash drops from 5,579 to 696 items. Of those typed, 3,236 are now
  `float` (calibration constants such as 14.7, -40.0 or 3500.0), 868 `ushort` or `short`,
  715 `byte` or `sbyte` and 64 `int`, `uint` or pointer. With RAM, 13,309 variables are
  typed.
- the warning about globals overlapping smaller symbols is left in 38 of 6,381 functions
  instead of 2,422 (the rest access peripherals)
- decompiled code has 70% fewer local variables of undefined type (3,349 to 1,017), 47%
  fewer undefined parameters (1,131 to 596) and 55% fewer `(float)` casts (2,631 to 1,189)

To apply both analyzers to an existing program, run them with **Analysis > One Shot**.

## Installation

Build the extension with Gradle and install the zip from `dist/` with
**File > Install Extensions** in Ghidra:

```
gradle -PGHIDRA_INSTALL_DIR=<absolute path to Ghidra>
```

Alternatively clone this repository into `<Ghidra>/Ghidra/Extensions/`. That provides the
language but not the analyzer, whose Java code the Gradle build compiles. Ghidra compiles
the SLEIGH specification the first time the language is used.

`version` in `extension.properties` is the Ghidra release whose PowerPC files are included.
Ghidra warns when you install the extension into a different release.

## Usage

- Raw flash images: import with the **Raw Binary** loader, choose `PowerPC:BE:32:VLE-e200`
  and set the base address where the image sits in the device's memory map.
- RAM: the Global Data Types analyzer adds the MPC5746R RAM blocks at the end of the first
  analysis (see above). If you map memory yourself, do it after the first analysis for the
  same reason. A later full re-analysis with RAM mapped adds about 1,300 flash-to-RAM
  pointers on the test firmware, but keeps the code.
- Peripherals: avoid a block that reaches 0xFFFFFFFF. Erased flash reads 0xFFFFFFFF, and
  the Create Address Tables analyzer turned 579,000 erased words into pointers.
- ELF files: the importer lists the language for 32-bit big-endian PowerPC ELF files.

## Verification

- **Decoding:** every 16-bit encoding and every 32-bit encoding of the VLE primary
  opcodes, for two register field patterns (2.1 million instruction words). Compared
  with GNU objdump 2.42 (`-M e200z4,lsp`) and NXP's binutils 2.28 (`-M e200z4`). All
  e200z4 instructions decode; the differences are listed below.
- **LSP semantics:** 156,000 randomized single-instruction tests (with edge values) in
  Ghidra's p-code emulator, checked against an independent Python model of the manual's
  pseudo-RTL. All pass; see `tools/lsp_test`.
- **Test firmware** (MPC5746R, 4 MB flash):
  - analysis finds the same 300,927 instructions and 6,359 functions as the previous
    release
  - decompiling the first 2,000 functions: no failures, and 553 decompiler warnings
    instead of 2,312
  - floating-point code decompiles to correct expressions; the previous release produced
    wrong values for `efsmadd` and the integer to float conversions

### Differences from GNU objdump

- Encodings with nonzero reserved fields are not decoded, for example EFPU2 compares with
  bits 9-10 set, or `efsabs` with a nonzero rB.
- LSP encodings the manual defines as illegal are not decoded:
  - an odd rD or rS for instructions that use a register pair (binutils accepts it for
    `zvaddwss` and `zstddu`)
  - rA=0 in the update and modify forms
- binutils decodes `zvcmpgths` and `zvcmplths` as `zvcmpgthu` and `zvcmplthu`.
- binutils' `e200z4` option also covers the older e200z4 cores (SPE, double precision)
  and e500 features the MPC57xx core does not have. Those instructions are not decoded:
  `ev*`, `efd*`, branch buffer and external PID cache locking, `mfdcrx`/`mtdcrx`, and
  TLB instructions.
- Ghidra's unmodified PowerPC files also decode some instructions the e200z4 lacks in VLE
  mode: string instructions, 4xx cache instructions, DCR and TLB access. Some mnemonics
  are also shown differently, for example `isellt` or `mfspr r0,CTR`.

### Modelling notes

- EFPU2:
  - conversions to integer truncate; out-of-range and NaN inputs are not saturated
  - SPEFSCR is not updated
  - compares set the GT bit of the CR field
  - the fused multiply-adds round twice
- LSP: see the header of `e200_lsp.sinc`:
  - signed-by-unsigned multiplies treat rA as signed
  - circular buffer indexes wrap at the end of the buffer
  - exceptions are not modelled
- Decorated storage, cache bypass and MPU instructions are opaque p-code operations.
- There are no VLE-specific function start patterns yet. Ghidra's PowerPC big-endian
  patterns apply to this language.

## Maintenance

| Tool | Purpose |
|------|---------|
| `tools/sync_upstream.py <ghidra> [--check]` | Copy Ghidra's PowerPC files from a source tree or installation and set the extension version |
| `tools/gen_pspec.py [--check]` | Generate `ppc_32_e200.pspec` |
| `tools/gen_lsp.py [--check]` | Generate `e200_lsp.sinc` from `tools/lsp_opcodes.txt` |
| `tools/lsp_test/` | Emulator tests of the LSP semantics |

`E200AddressAnalyzer.java` is derived from Ghidra's
`Ghidra/Processors/PowerPC/src/main/java/ghidra/app/plugin/core/analysis/PowerPCAddressAnalyzer.java`.
When syncing, check that file for changes worth carrying over.
