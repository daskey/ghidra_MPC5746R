# Ghidra processor module for the NXP e200z4 (MPC5746R)

A Ghidra language for the e200z4 PowerPC core of NXP MPC57xx microcontrollers such as
the MPC5746R: VLE-only code, 32-bit GPRs, EFPU2 single-precision floating point, the
Lightweight Signal Processing APU (LSP) and the core MPU. Its analyzer turns a raw flash
image into typed, decompilable code: entry points, functions, RAM and peripheral
registers, and the types of globals, parameters and return values.

| Language ID              | Description                                                       |
|--------------------------|-------------------------------------------------------------------|
| `PowerPC:BE:32:VLE-e200` | NXP e200z4 (MPC57xx, e.g. MPC5746R) 32-bit big endian, VLE only, EFPU2, LSP |

## Contents

The language includes Ghidra's own PowerPC SLEIGH sources unmodified (see
`data/languages/UPSTREAM` for the revision) and adds everything e200z4-specific in
separate files:

- `e200_efpu2.sinc`: EFPU2 scalar single precision (`efs*`) for 32-bit GPRs, including
  the fused multiply-adds, `efssqrt`, `efsmax`/`efsmin` and the half-precision conversions.
  Ghidra's SPE versions assume 64-bit GPRs.
- `e200_lsp.sinc`: all 678 LSP instructions with their full semantics: saturation,
  rounding, SPEFSCR overflow bits, register pairs, and circular and bit-reversed
  addressing. Generated by `tools/gen_lsp.py`.
- `e200_isa.sinc`:
  - MPU (`mpure`, `mpuwe`, `mpusync`), decorated storage including the cache bypass forms,
    `wait`, `e_ldmvmcsrrw`/`e_stmvmcsrrw`, `nego`, `lwarx` with EH=1, `dcbt`/`dcbtst` with a
    cache target
  - the saturated math of the e200z425 (`e_addwus`, `e_addhus`, ..., `e_addwss`)
  - corrections of Ghidra's VLE instructions:
    - `e_ori.` no longer decodes as `e_nop`; `e_cmp16i` and related instructions are no
      longer shown as record forms
    - the conditional branch and link (`e_beql`, `e_bdnzl`, ...) sets LR whether or not it
      is taken, and calls its target instead of the address stored at the target
    - `e_rlwinm` and `e_rlwimi` with a mask that wraps around (MB > ME) keep bits MB and ME
    - `se_srw` and `se_sraw` shift by 6 bits of rY; `se_sraw` and `se_srawi` set CA only
      when 1 bits are shifted out of a negative value
    - `se_bctr` and `se_bctrl` go to CTR as is, so calls through function pointers do not
      decompile as `(*(code *)((uint)p & 0xfffffffe))()`
- `ppc_32_e200.pspec`: e200z4 SPR names (`MCSRR0`, `DSRR0`, `MAS0`-`MAS3`, `MPU0CSR0`,
  `L1CSR0`, `HID0`, ...), VLE decoding everywhere, and which of Ghidra's analyzers run.
  SPRs that the hardware changes between accesses (timebase, DEC, DBSR, TSR, MCSR,
  MAS0-MAS3, and cache, branch buffer and MPU control) are volatile, so that the decompiler
  keeps the loops that poll them. Generated by `tools/gen_pspec.py`.
- `ppc_32_e200.cspec`: the PowerPC EABI of e200 compilers: arguments in r3-r10, floats
  included; results in r3 (r3:r4 for 8 bytes, and structures of up to 8 bytes); unsigned
  `char`; r2 and r13 (small data area bases) preserved; no `__get_pc_thunk_lr` call fixup,
  which models a classic PowerPC idiom that VLE code cannot execute.
- `data/patterns/e200_VLE_patterns.xml`: VLE function start patterns (the prologues
  `se_mflr r0; se_stw r0,4(r1)`, `e_stwu r1,-X(r1)`, ... after returns, branches, padding
  or erased flash), used instead of Ghidra's classic PowerPC patterns, which VLE code does
  not contain.
- `data/svd/MPC5746R.svd.gz`: NXP's CMSIS-SVD description of the MPC5746R peripherals,
  under the license in the file.

## Analyzer

One analyzer, **PowerPC e200** (`E200Analyzer.java`), does all the analysis below and runs
by default for this language; each step has its options under it in **Analysis Options**.
It runs on the code that analysis finds, where Ghidra's constant reference analyzers run:
it finds entry points, assumes the small data area bases and propagates constants. It
schedules the peripherals, functions and data types steps later in analysis, after
Decompiler Parameter ID, for the functions it has not handled yet. To apply it to an
existing program or a selection, run it with **Analysis > One Shot**.

### Entry points

`E200EntryPoints.java` finds the entry points of raw flash images, in memory not searched
before (option **Find boot headers and interrupt vectors**):
- **Boot headers** of the MPC57xx boot assist flash (`0x005A....` at the start of a flash
  block or a 16 KB boundary): typed `MPC57xx_boot_header`, with a function `reset` (or
  `reset_0`, `reset_1`, ...) at each core's reset vector.
- **Interrupt vector tables**: at least 8 vectors of `e_b` to a handler, 16 bytes apart
  from a 256-byte boundary, labeled `IVOR0_CriticalInput` to `IVOR34_EfpuRoundException`,
  with the handlers made functions.

### Small data area bases and constant references

`E200ConstantPropagation.java` is derived from Ghidra's PowerPC Constant Reference
Analyzer, which the processor spec disables, as it does the Basic one.
- **Small data area bases.** The analyzer assumes the EABI bases r13 (`_SDA_BASE_`) and r2
  (`_SDA2_BASE_`) in executable memory, so that `e_lwz r3,-0x7ff0(r13)` resolves to a
  global. The values come from register values already set (never changed), the linker
  symbols, or the startup code that loads the registers, found even where analysis does
  not reach it. When an image holds several programs, such as a bootloader and an
  application, each value applies to the code its startup code reaches, up to the erased
  flash before the next program; code copied to local memory gets the values of the
  program it was copied from. Option **Assume small data area bases**.
- **VLE instructions.** No references from `e_lis`, which holds only the upper half of an
  address, or from constants loaded with `e_li`, `se_li`, `se_bgeni` and `se_bmaski`.
- **Switch tables** behind `se_bctr`, bounded by VLE compares, also in flash images loaded
  into a writable block. Option **Switch Table Recovery**.

### Peripherals

`E200Peripherals.java` adds the 101 MPC5746R peripherals from the SVD description (option
**Add MPC5746R peripherals**): a volatile, uninitialized block and a structure of registers
at each base address, at the end of analysis like the RAM blocks. Peripheral code then
decompiles as

```c
INTC.PSR[0x1b] = 0;
FCCU.CTRLK = 0x913756af;
MEMU.SYS_RAM_CERR[i].STS = 0xff;
INTC.CPR[core] = 0xe;
```

instead of `_DAT_fc040076 = 0` and so on.
- Arrays of registers become arrays (`SIUL2_SVD_GEN.MSCR[12]`), registers repeated for each
  channel arrays of structures (`DMA_0.TCD[ch].SADDR`), and registers listed one by one as
  `NAME0`, `NAME1`, ... at consecutive addresses arrays (`INTC.CPR[2]`).
- Peripherals with the same registers share a type named after their group (`DSPI_Type`).
- Register comments give the description and the field masks (`Fields: MDIS=0x2 FRZ=0x1`).
- Space the SVD does not describe is typed as words named by offset (`field_0xc90`).
- Tables of two or more peripheral base addresses, as drivers for several instances of a
  peripheral use, become pointers to the peripherals' structures (`base->UARTSR = 0x3d04`).
- Option **Register bit fields** types registers as bit field structures instead of plain
  integers: tests then name the field (`FCCU.CTRL.OPS != 3`), but whole-register writes get
  casts.

### Functions

`E200Functions.java` completes the functions after Decompiler Parameter ID, in three steps,
each with an option:
- **Find functions in gaps** (`E200CodeGaps.java`): leaf functions that nothing calls
  directly, such as getters and state machine handlers reached through tables, match no
  start pattern. A gap after a return or unconditional branch becomes functions when all of
  it decodes as complete subroutines that stay in the gap, use no `se_illegal` and none of
  the instructions typical of data decoded as code that the program does not otherwise use.
  Each such function gets an analysis bookmark.
- **Calling conventions for kept registers** (`E200KeptRegisters.java`): e200 compilers
  know which volatile registers (r0, r3-r12) the functions they compile change, and keep
  values in the others across calls, which the decompiler showed as `extraout_` variables.
  The analyzer works out the registers each function changes, through its callees, and
  gives a function whose callers rely on it a calling convention that lists the registers
  it keeps as unaffected, such as `__keeps_r3to6_r8to12`, added as a specification
  extension. Decompiler Parameter ID then runs again for the callers whose view of a call
  changed.
- **Signatures of interrupt handlers**: functions whose returns are all interrupt returns
  (`se_rfi`, `se_rfci`, ...) get `void f(void)`. A handler restores r3 and r4 before
  returning, which Decompiler Parameter ID took for parameters and a result.

Signatures set by the user or an import are left alone.

### Data types

`E200DataTypes.java` and `E200TypeFlow.java` type global data, parameters and return values
that are still `undefined1`, `undefined2`, `undefined4`, ... after Decompiler Parameter ID,
from what the decompiler infers in all functions (option **Infer data types**; this
decompiles every function and is the longest part of the analysis):
- **Globals from their uses**: a value used by `efs*` instructions is a `float`, one that is
  sign extended is signed, one that is dereferenced is a pointer. A type is applied only
  when the uses agree, except that a `float` wins over integers of its size and integers
  that differ in signedness go to a clear majority. Single bytes become `byte` or `sbyte`.
- **Arrays and tables**: arrays that code indexes get data of the element size at their
  start, and addresses used as pointers to a type get data of that type, as in
  `(&BYTE_4000e46e)[i]` and `FUN_08faf3e0(&SHORT_09294ba0, x)`.
- **Values passed between functions**: a function that only stores, passes on or returns a
  value gives it no type, but the value has one where it comes from or goes to. Globals,
  parameters and return values are linked where decompiled code copies a value from one to
  another, and each group of linked places gets the type all their uses agree on. A
  parameter or return value is typed only when all callers of its function were decompiled.
- New types change the decompiled code of the functions that use them, so the analyzer
  decompiles again those that still use undefined places, or use a place now typed as a
  pointer (which shows the data it points to), three rounds at most.
- **Unsigned types for untyped values** (option): places whose group shows no type at all,
  values that are only copied, compared for equality or accessed in bytes, get the unsigned
  integer of their size, and pointers to undefined data of 1, 2 or 4 bytes a pointer to it,
  unless a linked value is a pointer, a `float` or of another size. Functions that return
  nothing, whose result no caller reads, get the return type `void`, which Decompiler
  Parameter ID leaves undefined.

A flash image has no RAM, so RAM variables have no data and the decompiler shows them as
`_DAT_40001234`. The analyzer therefore first adds uninitialized blocks for the MPC5746R
RAM where nothing is mapped (`SRAM` at 0x40000000, `IMEM_0`/`IMEM_1` at 0x50000000 and
0x51000000, `DMEM_0`/`DMEM_1` at 0x50800000 and 0x51800000; around a dump of part of a RAM,
blocks such as `SRAM_40000000`) and creates data of the accessed size where code
references them. It does this at the end of analysis: with RAM mapped from the start,
Ghidra's Create Address Tables analyzer takes flash values such as the float 2.0
(0x40000000) for pointers into RAM. Option **Add MPC5746R RAM blocks**.

### Memory dumps

`ghidra_scripts/AddMemoryDumps.java` (category **PowerPC e200**) adds the dumps in a folder
to the current program, each at the range its file name ends with, as in
`sram_40000000-4003FFFF.bin`: RAM as read/write, local instruction memory also executable,
the data flash at 0x00800000 as read/write, anything else as read/write/execute. A dump
fills an empty RAM block that analysis added; one over initialized memory is skipped. Run
analysis afterwards: it finds the code in the dumps and assumes r13 and r2 there.

## Results

On 11 flash images of the test firmware (several releases of an MPC5746R application with
its bootloader, 4 MB each), analyzed with the default options and every function
decompiled, per image:

| | Mean | Range |
|---|---|---|
| Functions | 14,427 | 13,891-14,918 |
| Instructions | 445,380 | 418,579-464,539 |
| Decompiler failures | 0 | 0 |
| Functions with decompiler warnings | 86 | 83-89 |
| Functions with `undefined` in their signature | 246 | 246 |
| Functions with `extraout_` variables | 7 | 7 |
| `undefinedN` in the C | 2,998 | 2,767-3,126 |
| `DAT_` references in the C | 1,199 | 1,140-1,231 |
| Analysis time (2 CPUs) | 126 s | 118-131 s |

Most decompiler warnings are about infinite loops (halt loops) and unreachable blocks the
decompiler removes. The data types step takes 37% of the analysis time, Decompiler
Parameter ID 20%.

## Installation

Build the extension with Gradle and install the zip from `dist/` with
**File > Install Extensions** in Ghidra:

```
gradle -PGHIDRA_INSTALL_DIR=<absolute path to Ghidra>
```

Cloning this repository into `<Ghidra>/Ghidra/Extensions/` provides the language but not
the analyzer, whose Java code the Gradle build compiles. Ghidra compiles the SLEIGH
specification the first time the language is used. `version` in `extension.properties` is
the Ghidra release whose PowerPC files are included.

## Usage

- Raw flash images: import with the **Raw Binary** loader, choose `PowerPC:BE:32:VLE-e200`
  and set the base address where the image sits in the device's memory map. An image with
  a bootloader and an application can be imported as one file.
- RAM and peripherals: if you map memory yourself, do it after the first analysis, for the
  reason above, or use `AddMemoryDumps.java`. Avoid a block that reaches 0xFFFFFFFF: erased
  flash reads 0xFFFFFFFF, and Create Address Tables turns erased words into pointers.
- ELF files: the importer lists the language for 32-bit big-endian PowerPC ELF files.

## Verification

- **Decoding:** every 16-bit encoding and every 32-bit encoding of the VLE primary opcodes,
  for two register field patterns (2.1 million instruction words), compared with GNU
  objdump 2.42 (`-M e200z4,lsp`) and NXP's binutils 2.28 (`-M e200z4`). All e200z4
  instructions decode; the differences are below.
- **LSP semantics:** 156,000 randomized single-instruction tests in Ghidra's p-code
  emulator against an independent Python model of the manual's pseudo-RTL; all pass. See
  `tools/lsp_test`.
- **VLE semantics:** 90,000 randomized single-instruction tests of 199 integer, branch,
  load/store and EFPU2 instructions against an independent Python model of the Power ISA;
  all pass (5,259 failed with Ghidra's semantics). See `tools/vle_test`.

### Differences from GNU objdump

- Encodings with nonzero reserved fields are not decoded, for example EFPU2 compares with
  bits 9-10 set, or `efsabs` with a nonzero rB.
- LSP encodings the manual defines as illegal are not decoded: an odd rD or rS for
  register pair instructions, and rA=0 in the update and modify forms.
- binutils decodes `zvcmpgths` and `zvcmplths` as `zvcmpgthu` and `zvcmplthu`.
- Instructions of older e200 and e500 cores that the MPC57xx core lacks are not decoded:
  `ev*`, `efd*`, branch buffer and external PID cache locking, `mfdcrx`/`mtdcrx`, TLB.
- Ghidra's unmodified PowerPC files also decode some instructions the e200z4 lacks in VLE
  mode (string, 4xx cache, DCR and TLB access), and show some mnemonics differently.

### Modelling notes

- EFPU2: conversions to integer do not saturate out-of-range and NaN inputs, and round a
  value halfway between two integers up instead of to even; SPEFSCR is not updated;
  compares set the GT bit of the CR field; the fused multiply-adds round twice.
- LSP (see the header of `e200_lsp.sinc`): signed-by-unsigned multiplies treat rA as
  signed; circular buffer indexes wrap at the end of the buffer; exceptions are not
  modelled.
- Decorated storage, cache bypass and MPU instructions are opaque p-code operations.
- `se_bctr` and `se_bctrl` do not clear bit 0 of CTR.

## Maintenance

| Tool | Purpose |
|------|---------|
| `tools/sync_upstream.py <ghidra> [--check]` | Copy Ghidra's PowerPC files from a source tree or installation and set the extension version |
| `tools/gen_pspec.py [--check]` | Generate `ppc_32_e200.pspec` |
| `tools/gen_lsp.py [--check]` | Generate `e200_lsp.sinc` from `tools/lsp_opcodes.txt` |
| `tools/lsp_test/` | Emulator tests of the LSP semantics |
| `tools/vle_test/` | Emulator tests of the VLE integer, branch, load/store and EFPU2 semantics |

The tools are not part of the extension zip. `E200ConstantPropagation.java` is derived from
Ghidra's `PowerPCAddressAnalyzer.java`; when syncing, check that file for changes worth
carrying over.
